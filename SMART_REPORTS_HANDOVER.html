How it works

ReportVersion (FINALIZED — snapshot already frozen, ranges + flags resolved)
      │
      ├─ eligibility      rules   → is there a Smart-Report-enabled package on this visit?
      ├─ findings         rules   → value · unit · range · status · direction
      ├─ score + rollup   formula → 0–100, per-panel counts (ONE set, so they can't disagree)
      ├─ trends           SQL     → prior finalized value, unit-matched only
      ├─ content          JOIN    → HealthContentRule + follow-up tests the lab actually sells
      │
      ├──────────── everything above is deterministic and unit-testable ────────────
      │
      ├─ LLM              ONE call, TWO blocks: the Test Score paragraph + the Advisory page
      ├─ validator        rules   → schema · numbers grounded · banned lexicon · catalog membership
      │                             fail → retry once → fall back to template copy
      └─ renderer → HTML → PDF (existing Puppeteer) → Redis cache → token-gated URL
The one rule everything follows from. The LLM receives a closed, de-identified set of facts and may only re-word them. It never produces a number, a status, a test name, a score, or a decision about which test to suggest — and a validator rejects any number in its output that wasn't in its input.

Decisions that shape everything

1. Reads one frozen row, never the live catalog

Everything comes from ReportVersion.panelsSnapshot, which already holds age/sex-resolved reference ranges and flags. One primary-key read — and a later price or range edit can never retroactively change a patient's old report.

2. The clinical report is never touched

Smart Report is a separate document at a separate URL. Not prepended to the merged PDF, no changes to panelsSnapshot, no signature block. It carries no doctor's signature because it is explicitly not a signed clinical document.

3. Generation can never break a finalize

Fire-and-forget off the finalize route, the same shape as sendReportReady. Four lines inside existing files. If it throws, the finalize is unaffected and the patient still gets their normal report.

4. Score and panel tiles come from one finding set

The reference report we cloned prints "all 89 parameters normal, score 100%" beside tiles reading 7 Abnormal. That's the worst thing this product can do. Ours derives both from the same resolved set, and there's a regression test for it.

5. It never names a condition

HbA1c of 6.3 reads "above the recommended range", never "prediabetes". Naming the condition is a diagnosis and it's the doctor's job. Enforced by a banned lexicon in the validator, not by prompt politeness.

6. Nothing identifying is sent to the AI provider

No name, patient number, phone, visit number, branch or doctor — the model gets an age band, sex and the finding set, which is all it needs to write copy. Matters doubly with an overseas provider, and it closes the prompt-injection path since no patient free text ever reaches the model. Enforced by a unit test on the payload builder.

Scope — who gets a Smart Report

It's a property of the package, not the visit. A one-off Lipid Profile produces nothing; a Master Health Check does. New field BillableProduct.smartReportEnabled, shown in the product editor only for bundles, and only switchable when the resolved package has:

  • no EXTERNAL_UPLOAD line — an uploaded PDF has no structured values
  • no TEXT_ONLY or IMAGING_NARRATIVE panel — free text has no ranges to score

PROCEDURE_STRUCTURED and BILL_ONLY child lines are explicitly allowed — the first is structured despite its neighbours in the enum, the second carries no results and simply contributes nothing.

Extras on the same visit don't disqualify it: a Master Health Check plus a USG still generates, scoped to the package, with the USG listed as "reported separately". Two enabled packages produce one report. Scope resolves from TestOrder.productId, so a later catalog edit can't rewrite history.

The cases that usually get missed

Critical results

A score of 71 beside a critical potassium is indefensible. Any critical value replaces the score with "contact the centre today", sorts that card first, and suppresses the advisory page entirely. That patient should be phoning the lab, not reading a diet page.

Children

Adult calorie and macro formulas are wrong for a child. Below a configurable age (default 18) we skip the report rather than print bad advice.

Pregnancy

HealthFlow has no pregnancy flag. If a resolved range is labelled for pregnancy, the advisory page is suppressed and the report says the ranges were interpreted that way. Proper handling is a V1 registration field.

Null vs zero

An unresulted test is excluded from every count — never silently counted as normal. That's the reference report's bug wearing a different hat.

Operator results

<0.1 is never parsed into 0.1. A parsed operator is a fabricated value; it's listed, not scored.

Puppeteer OOM

This codebase has already had one on 512 MB. Smart Report PDFs render lazily on first request through the existing concurrency limiter — finalize writes a row and never launches a browser.

Batch finalize

60 reports at 6pm would fire 60 concurrent LLM calls and rate-limit the provider, silently degrading the whole evening to template copy. Queue with concurrency 3.

Page numbering

Page count varies — Health Essentials is omitted without height/weight, cards paginate, the advisory disappears on a critical. Numbers are computed, never hardcoded.

Self-audit — what the first pass missed

I specified a duplicate of a system you already have

HealthFlow already has a per-analyte rule engine — InterpretationRule plus matchInterpretationRule(), with numeric operators and text matching, already evaluated into interpretationsSnapshot. I designed HealthContentRule from scratch with the same trigger shape. Corrected: reuse the matcher, keep patient-facing text separate (the existing text names conditions and can't go to patients), and seed the catalog from those rules — the lab has already decided which analytes matter and what they mean.

Patients already under treatment

A managed diabetic's HbA1c of 7.5 is their doctor's target, not a finding. HealthFlow holds no medication history, so the report cannot know — it would tell them they're "above the recommended range" and suggest avoiding sweets. The disclaimer now always carries: "If you are already being treated for a condition, your doctor's targets for you may differ from the general ranges used here." Cheapest safety line in the product.

False reassurance was missing from the banned lexicon

I had diagnosis words, drug names and prognosis. I'd missed that "nothing to worry about" and "no need to see a doctor" are as dangerous as a false alarm — the model cannot know either. Now its own category.

Build order

Start the content catalog on day one — it's the long pole, and it's the only item that can't be parallelised away. Everything else follows: schema → deterministic engines → AI layer + validator → renderer → delivery routes → frontend → the edge-case test suite → ship with the flag off, enable for one branch, review a week of output, then turn it on.

Three calls I'd like from you

  • The score formula. Start at 100, −4 per out-of-range, −1 per borderline, capped at −10 per panel. Our example patient scores 59. Does that feel right for your patients?
  • Never naming a condition. Safe and defensible, but some owners want the report to be more explicit. It's a one-line change to the lexicon — and one I'd argue against.
  • The catalog gate. No content rule ⇒ no explanation, just a row and a status. Maximally safe, but the report is thin until the catalog is filled.
