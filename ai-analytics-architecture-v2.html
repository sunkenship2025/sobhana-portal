The design principle the measurements force

Retrieval's job is to keep the prompt small, keep token/PHI tables out of it, and scale past 73 tables. All three are real. None of them is the accuracy story. The accuracy story is the metric layer — and the honest corollary is that answers from defined metrics are exact, while answers from generated SQL carry irreducible definitional variance and must be labelled differently in the UI.

Retractions

Two V1 claims were asserted without evidence. The test killed both.

RETRACTED  "A big schema causes wrong-table and wrong-timestamp errors"

It doesn't. Handed all 73 tables raw, DeepSeek got both traps right — including LabTest(243, legacy) vs TestDefinition(443) vs TestOrder(29,784), and choosing finalizedAt over createdAt. I was underrating the model.

RETRACTED  "Retrieval buys latency"

1,594 ms retrieved vs 1,490 ms full-schema. The retrieved arm was marginally slower. At 6k input tokens prefill is not the bottleneck. Do not use latency to justify this architecture.

CONFIRMED, DECISIVELY  "The metric layer prevents contradictory numbers"

Asked "what was our revenue in August?" with only the schema, the model invented SUM("paidAmountInPaise") WHERE "paymentStatus"='PAID' — plausible, executable, wrong. With the metric expression injected, it was exact. This single result is the reason the architecture looks the way it does.

Also retracted: the V1 headline "don't build text-to-SQL, build text-to-plan." A closed DSL cannot express "how many patients had more than two tests in the last 90 days" — exactly the long tail the feature exists for. Metrics constrain; they do not cover.

The surprise: metric injection can hurt

Question 4 failed in the retrieved arm at 99 instead of 1,456. Retrieval was not at fault — TestOrder was retrieved. The cause was the instruction header DEFINED METRICS — use these expressions VERBATIM: the model forced a per-patient HAVING question into the shape of the unique_patients metric.

One targeted call confirmed the diagnosis. Softening the header produced the correct TestOrder ⋈ Visit … GROUP BY "patientId" HAVING COUNT(*) > 2:

REFERENCE METRIC DEFINITIONS — use ONLY if the question asks for exactly this
quantity. If it needs a different grain (per-patient, per-order, HAVING),
IGNORE these and write SQL from the TABLES below.
Rule

A metric is a definition on offer, not a template to force the question into. Metric headers must be soft, with an explicit escape clause.

The central finding

Valid SQL. Sensible semantics. Passes every validator. Executes without error. Wrong by 3%.

After the soft header fixed the semantics, the query still failed on unquoted camelCase (t.cancelledat). A deterministic repair — quote any known camelCase identifier, built from information_schema, zero LLM calls — fixed the syntax. The query then ran clean and returned:

1,456
hand-written control
1,410
model, repaired, no error signal
SELECT COUNT(*) FROM (
  SELECT v."patientId" FROM "Visit" v JOIN "TestOrder" t ON t."visitId" = v.id
  WHERE v."createdAt" AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Kolkata'
        >= (CURRENT_TIMESTAMP AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Kolkata')
           - INTERVAL '90 days'
    AND t."cancelledAt" IS NULL
    AND t."noReportAt" IS NULL          ← extra filter the control did not have
  GROUP BY v."patientId" HAVING COUNT(t.id) > 2) AS sub;
                ↑ filtered on VISIT date, control used ORDER date
Why this shapes everything

Both readings are defensible. No schema context, no SQL parser, no EXPLAIN, no read-only role and no retry loop can detect this. Only a defined metric eliminates it — and only for the questions a metric covers.

The consequence is a product decision, not a technical one:

Metric-backed answer

States the number. Certified. Reconciled against the Money page at zero tolerance in CI. "Revenue in August was ₹18,93,725."

Generated answer

States the number and the assumptions it rests on, visibly, and is labelled as generated rather than certified. "1,410 patients — counting by visit date, excluding films-only orders."

Measured regression worth keeping

My first version indexed all columns including *Id. Because branchId appears in ten tables, the word "branch" stopped discriminating, the Branch table fell out of the top-N, recall dropped and tokens doubled. FK columns are join plumbing, not semantics — exclude them from the keyword index.

What the value index catches that hand-written keywords miss

"hba1c"  → TestOrder.testCodeSnapshot IN ('GHB','HBA1C','HBA1C_OUTSIDE')
                                            ↑ three codes. A hand-written list
                                              returns one and silently halves the answer.

branch   → really spelled "Jagathgiri Gutta", not the "Jagadgirigutta"
           I had hand-typed into the catalog.

Verdict on embeddings: no. An embedding index needs a model, a store, a refresh pipeline and ~30–80 ms per query, to beat 100% recall. It cannot. Revisit only if the catalog exceeds ~200 tables, or if the retrieval_low_confidence counter shows users reaching for vocabulary the catalog and value index don't contain.

Ambiguity — default and disclose, never block

  1. Matches a defined metric → use it, state the definition in provenance.
  2. Two metrics tie ("patients" = visits or people) → answer the common reading, say which, offer the other as a chip.
  3. No time range → current month, stated.
  4. Long tail, no metric → generate SQL and show the assumptions next to the number.
  5. Ask a clarifying question only when an entity fails to resolve ("HbA1c or Hb?") — never for a definitional choice we can default.

Two honest caveats

DeepSeek reports prompt_cache_hit_tokens — a static full schema would cache well, narrowing Architecture 1's gap. And at current volumes every option is affordable. Choose on accuracy and on not leaking token/PHI tables into the prompt. Cost merely confirms the choice.

Why this beats the full schema — only 3 of 5 reasons survived

✓ Metric adherence

Decisive. Worth 7%+ on the number that matters most.

✓ Sensitive tables never in the prompt

The full-schema arm sent ReportAccessToken, BillAccessToken, PatientIdentifier and User.passwordHash to an external API on every question. A privacy property of the prompt itself.

✓ Decommissioned twins excluded

13 tables are empty; LabTest(243) shadows TestDefinition(443). Insurance, not a demonstrated win — but it scales the wrong way.

✗ Latency

Measured no gain. Dropped.

✗ "Can't find the table"

It could. Dropped.

Define centrally when a wrong answer looks right. Generate when a wrong answer looks wrong.

Your decision — revenue defaults to net collected

Locked in. Measured for August 2026, the gap is small because this centre collects at point of service, so the change is low-risk:

Gap: ₹7,200 — 0.4% of billed. Two consequences to note:

  • "Collected" itself has two readings, ₹7,000 apart: transactions dated in the period (cash-flow, recommended default) vs cash against bills billed in the period (collections performance). The AI will use the cash-flow reading and say so.
  • Net billed doesn't disappear — it stops owning the word "revenue" and becomes net_billed. It's still needed: outstanding is computed from it, and the sanity check collected(cohort) + outstanding = net_billed reconciles to the rupee.
  • ⚠️ The Money page headline KPI is still net billed. Either the page's label or the AI's default should move so the two agree — worth deciding before V1 ships.

MUST be defined (~15 for V1)

Every money metric — collected (now "revenue"), net_billed, outstanding, discount_total, refund_total, commission. Every ratio — abnormal_rate (the 38%-NULL denominator), cancellation_rate, delivery_rate, collection rate. Plus tat_p50, reports_finalized (latest-version rule), visits vs unique_patients, test_orders.

Safe to generate

Anything whose error is visible: counts and group-bys over one fact table, top-N rankings, distributions, existence questions — and all multi-condition / HAVING / cohort questions, which cannot be pre-defined and which the model writes correctly given the right context.

Cap V1 at ~20 metrics. "Patient volume", "workload", "how are we doing" are aliases resolved by the keyword index — not new definitions.

V1 scope

The smallest thing that is genuinely useful.

  1. analytics_ro read-only Postgres role + grants — the gap: only neondb_owner exists today.
  2. AI Metadata Catalog — 26 tables, hand-authored descriptions + aliases. ~2 days, and the highest-value work in the project.
  3. Metric registry — 15 metrics, each with reconcileWith anchored to the existing owner*Service numbers.
  4. Deterministic retriever — the code measured on this page. ~200 lines.
  5. Validator + deterministic camelCase repair.
  6. One DeepSeek call via the existing smartReport/llm.ts — add an optional system param; do not write a second client.
  7. Template responses for single values; LLM prose only for multi-row.
  8. AnalyticsQueryLog + 40-case eval harness, money reconciled at zero tolerance.
  9. Owner-only UI reusing ownerUi.tsx + recharts.

Not in V1: embeddings · multi-agent anything · conversation · charts beyond line/bar/KPI · anomaly narration · raw-SQL escape hatch · materialized views.

V2: conversation via structured state (~150 tokens, never the transcript) · "why did X change" decomposition · AnomalyEvent-backed "anything unusual" · scheduled digests · catalog auto-drafting · embeddings only if the low-confidence counter proves a gap.
