AI Analytics Layer

A general-purpose natural-language analytics surface over the entire application database — built so that every number comes from Postgres, every definition comes from one registry, and the model never writes a character of SQL.

The one decision

Don't build text-to-SQL. Build text-to-query-plan.

The LLM translates a question into a small typed JSON object naming a metric, dimensions, filters and a time range. The application compiles that object into SQL from developer-authored fragments. The model contributes zero characters of SQL.

A semantic layer already exists

~4,300 lines across five owner*Service.ts files already encode what "net revenue", "collection rate" and "TAT" mean here. Free-form SQL invents a second, contradicting definition. Two revenue numbers on two screens is worse than no analytics.

The money math is not guessable

Net revenue is total − discount − coupon − reversedCharge. "Paid" nets REFUND rows out of PAYMENT rows. Referral commission is pct-of-gross minus the full order discount. A model shown the schema gets these wrong — and wrong plausibly.

Injection becomes absent, not blocked

There is no parser to outsmart because there is no attacker-influenced SQL text. Tenant scope is injected by the compiler from req.branchId; the plan can only filter within granted scope, never widen it.

Escape hatch

A guarded raw-SQL path is still worth building — as Phase 6, owner-only, behind a read-only role and an AST allowlist, and only if the unanswerable log proves the DSL is the bottleneck. Not on day one.

Structural catch

Every existing owner metric computes in TypeScript — findMany a row set, then .reduce(). They cannot be lifted as SQL fragments. Definitions must be re-expressed once in the registry, and reconciled numerically against the live pages. That reconciliation is a hard Phase-0 gate, not a nicety.

Ten weeks of history

Earliest visit is 2026-07-01. Jul 2,040 · Aug 2,256 · Sep 769 visits. "This quarter vs last quarter", "year-over-year" and "6-month HbA1c trend" have no data behind them. The system must say so — explicitly, every time. This is the single highest-value correctness behaviour in the feature and it is a four-line check against MIN(Visit.createdAt).

Everything is a fast full scan

A full-table GROUP BY over Bill ⋈ Branch with IST bucketing returns in 1.5–3.2 s including Neon cold-start, sub-second warm. So: build no performance infrastructure. No materialized views, no cube, no warehouse. Revisit around 500k test orders — roughly 2028 at current volume.

What the database can and cannot answer

Answerable today

Revenue (gross/net/collected/outstanding/aging/discounts/refunds/commission) · visit & patient volume · test and panel volume by snapshot code · department and payout-category mix · turnaround time p50/p95 against the existing 1440-min SLA · queue depth · cancellation and completion rates · WhatsApp delivery rate · abnormal-result rate · referral-doctor and clinic-doctor attribution · outsourcing to external labs · staff collection split · audit anomalies.

Not in the schema — must refuse

Diagnoses. There is no diagnosis or ICD table. "Most common diagnoses" is unanswerable; the nearest true answer is most frequent abnormal test results.
Appointments. No appointment entity — "cancelled appointments" can only mean Visit.status = CANCELLED, a cancelled visit, which is worth saying out loud.
Also absent: room/equipment utilisation, staff rosters, cost of goods.

Deliberate consequence

The analytics layer is aggregate-only. No plan can return a patient-level row. Questions that need one ("which patients haven't paid", "which patients have high HbA1c") route to the existing Money page or worklist, which already have RBAC, audit and a UI built for it. Aggregate-only is not the same as "no clinical result analytics" — see below.

Clinical result values

The first draft banned TestResult.value outright. That was too blunt — and the DSL had no grammar for the good questions anyway.

The original filter grammar supported only in/not_in on categoricals, so "how many HbA1c results were above 6.5" was inexpressible, never mind forbidden. Probing the real data settles what opens and what stays shut.

✓ value — OPEN as a measure

21,120 of 30,581 results carry a number, across 85 test codes. Grouped by code it's genuinely useful — HB mean 11.67, FBS1 130.1, NEUT 59.95.

Ungrouped it is garbage: mean 480.94 over a range of −2 to 81,000, because it averages haemoglobin with platelet counts with glucose.

✕ textValue — CLOSED as a free dimension

27,721 rows, 2,233 distinct values — but 337 rows exceed 200 characters and 232 exceed 1,000, peaking at 6,968 characters of HTML radiology narrative (<p><u>FINDINGS:</u></p>…).

Exposing it as a GROUP BY label ships an entire imaging report body to DeepSeek inside a dimension label. A real exfiltration path, not a theoretical one.

Validator rule V-1 — correctness, not privacy

A result_* metric is invalid without exactly one resolved analyte scope. Reject with "which test did you mean?" rather than returning a number.

The values are dirty, and the mean lies

The sharpest new risk this probe surfaced:

An AI answering "average platelet count is 92.89" is confidently, embarrassingly wrong — precisely the credibility failure this whole design exists to prevent.

Validator rule V-2

result_* metrics default to median. Mean is available only when explicitly asked, and every value answer carries n, the count outside 10× reference range, and the count of non-positive values in its caveats.

The categorical subset that IS safe

Codes whose textValue is ≤25 distinct values and ≤40 characters — the whole CUE_* urine panel (CUE_COL, CUE_APP, CUE_RXN, CUE_PUS, CUE_RBC, CUE_EPI, CUE_CST, CUE_CRY, CUE_BP, CUE_BS, CUE_SG) plus PLTM, RBCM, WBCM. These answer real questions: "how many urine samples were turbid", "platelet morphology distribution".

Shipped as dimension result_category — an explicit human-reviewed test-code allowlist, with a runtime length(textValue) < 40 guard as a belt. .notes (2,859 rows of free text) stays closed entirely.

Trap 15 — duplicate analyte codes silently halve the answer

Ten analytes have two live codes for the same name: CRT|CREAT (serum creatinine), TCH|TOCHO (total cholesterol), STGL|TRIG, FBS1|GTTF, ELE|ELYTE, BS1HR|GTT1. "Show me the creatinine trend" against one code returns half the data with no error. resolve.ts must canonicalize name → set of codes, not name → one code.

Also confirmed: HbA1c is stored as GHB ("GLYCOSYLATED HAEMOGLOBIN(HBA1C)"). Your own example question is unanswerable without fuzzy name resolution — which promotes resolve.ts from a Phase-2 nicety to core.

What this opens, and what stays refused

New metrics

result_median · result_p90 · result_mean · result_min_max · result_count_matching (threshold count) · result_histogram (bucketed distribution) · result_category as a distribution dimension. New filter ops gt/gte/lt/lte/between, valid only on the value measure.

Still refused

Any patient-level result row · .notes · narrative textValue · cohort listing ("which patients had abnormal HbA1c") — that last routes to the existing worklist, which already has the RBAC and audit for it.

Rule of thumb

If getting it wrong produces a plausible number rather than an error, it must be a defined metric. That covers 100% of the money and 100% of the ratios.

End-to-end request flow

Seven stages. The model has authority in exactly two of them, and writes prose in only one.

Why validate before execute

It turns "the model was wrong" into a typed, machine-readable error before a query runs — unknown metric 'footfall'; valid: visits, test_orders, …. Most self-healing happens here, not against database errors.

Why facts and charts are deterministic

Every derived number (delta %, share of total, rank) and the chart type are computed in TypeScript, so they are unit-testable and cannot drift. No model ever picks a pie chart for a twelve-month trend.

The QueryPlan DSL

A closed vocabulary the validator can check exhaustively.

type QueryPlan = {
  v: 1;
  metric: MetricId;                     // 'net_revenue' | 'visits' | 'abnormal_rate' | …
  dimensions: DimensionId[];            // 0–2.  [] = a single number
  grain: 'day' | 'week' | 'month' | null;
  timeRange:
    | { preset: TimePreset }            // 'today' | 'this_month' | 'last_month' | 'last_7d' | …
    | { from: string; to: string };     // ISO IST dates, inclusive
  filters: Array<
    | { dim: DimensionId; op: 'in'|'not_in'; values: string[] }       // categorical
    | { measure: 'result_value';                                     // numeric — see
        op: 'gt'|'gte'|'lt'|'lte'|'between';                         // Clinical values
        value: number; value2?: number }
  >;
  analyte?: AnalyteId;              // REQUIRED for every result_* metric (rule V-1)
  compareTo: 'previous_period' | 'none';
  sort: { by: 'value' | 'label'; dir: 'asc' | 'desc' };
  limit: number;                        // 1–100, default 20
};

// The model returns { plan }  OR  { unanswerable: { reason, suggestion } }.
// Nothing else is accepted.
Key property

The model never does date arithmetic. It picks a preset from an enum; the application resolves it in IST against now(). LLM date math — especially across a +5:30 offset — is a top hallucination source, and this deletes the entire class.

What context the model gets

Not the schema. A hand-authored catalog of the metrics and dimensions it may name — about 1,200–1,800 tokens, static, so it is prompt-cacheable and costs essentially nothing per request.

This is the answer to "don't send the whole schema every time" — and a better answer than retrieval, because at ~20 metrics and ~16 dimensions the entire vocabulary fits in the prompt. Vector retrieval is not needed and should not be built.

The one thing genuinely retrieved: name → code. 443 test definitions, 337 products and 215 doctors don't belong in a prompt. The model emits {dim:'test', values:['HbA1c']}; the app resolves it to HBA1C with an ILIKE lookup, or returns "did you mean…" with the top 5. Deterministic, cheap, and it makes the model's job easier rather than harder.

SQL safety

The primary control isn't a validator. It's that there is nothing to validate.

The compiler assembles SQL from three sources only:

  1. Registry constants — developer-authored strings in version control.
  2. Bound parameters — every user and model value, including filter values and dates. Prisma tagged templates, never $queryRawUnsafe.
  3. Enum-checked identifiers — metric and dimension ids validated against the registry map before selecting a fragment. An unknown id is a rejected plan, never an interpolated string.
Gap to close first

Today the app connects as neondb_owner and no read-only role exists. Creating analytics_ro with a table and column allowlist is Milestone 0.1 — before the first query runs, before any LLM code is written.

Prompt injection

The surface is small by construction, but two real vectors remain and are handled: (1) a question crafted to make the narration assert something false — mitigated by numeric post-validation and by the UI treating data, not prose, as truth; (2) injected content arriving through dimension labels — a staff member renaming a product to "ignore previous instructions" — mitigated by delimiting and escaping labels in the narration payload and never treating row content as instructions. Both get dedicated eval cases.

Truth model

Every factual number comes from Postgres. The model writes captions.

LLM  → chooses a metric from a fixed list        (validated against the registry)
APP  → compiles and runs the SQL                 (LLM contributed no SQL)
DB   → produces every number                     (the only source of facts)
APP  → computes every derived number             (deltas, shares, ranks — in TS)
LLM  → writes prose about numbers it was handed  (and may not invent new ones)

Three enforcement mechanisms, strongest first

1 · Structural

The narration prompt receives pre-formatted value strings — "₹11,41,705", "+18.2%" — and is told to use those tokens verbatim. Numbers can't be generated because none are computed at that stage.

2 · Post-validation

Extract every numeric token from the narration; any token absent from the facts object drops the sentence. Exactly the dropResultClaims pattern already in production in Smart Reports.

3 · Provenance

The UI renders numbers from data, never from answer. Prose is a caption over a table. If narration fails entirely, a deterministic template ships and the answer is still correct.

Refusing well

unanswerable is a first-class success, not an error path. Four triggers: no such concept ("most common diagnoses" → offer abnormal results instead); out of coverage ("last quarter" → "we have data from 1 Jul only; here's Jul vs Aug"); ambiguous ("revenue" → answer with the definition stated, offer the other reading as a chip); not permitted ("financial metrics are owner-only" — never "no data", because misleading about permissions is its own failure).

Semantic layer

One definition per metric, anchored to a number already in production.

{
  id: 'net_revenue',
  label: 'Net revenue',
  unit: 'paise',
  description: 'Billed amount after manual discount, campaign coupon and voided ' +
               'charges. Not cash collected.',
  agg:  'SUM(b."totalAmountInPaise" - b."discountAmountInPaise" ' +
        '   - b."couponDiscountInPaise" - b."reversedChargeInPaise")',
  from: '"Bill" b JOIN "Visit" v ON v.id = b."visitId"',
  timeColumn:  'b."billedAt"',        // STABLE — never updatedAt
  branchColumn:'b."branchId"',        // how tenant scope is applied
  baseFilters: [],
  dimensions:  ['branch','domain','payout_category','product',
                'referral_doctor','payment_status','collected_by'],
  roles:       ['owner'],
  caveats:     ['Excludes ₹0 EVENT products.'],
  reconcileWith: 'ownerMoneyService.getOwnerMoney().kpis.netInPaise',   // ← eval anchor
}
reconcileWith

The load-bearing field. It names the existing production number this metric must equal, and the eval harness asserts it at zero tolerance for money. That is the mechanism that guarantees the AI and the Money page never disagree.

Must be defined centrally

Every financial metric (gross, net, collected, outstanding, aging, discount rate, refunds, commission, collection rate) · every ratio (abnormal, cancellation, delivery, within-SLA, completion) · TAT percentiles · reports finalized (latest-version rule) · referral attribution (soft delete + pct-of-gross-minus-full-discount) · anything touching TestResult.flag · anything spanning Visit ↔ Bill ↔ TestOrder.

Safe to express generically

Simple counts of one fact table grouped by one registered dimension — visits by branch, orders by workflow mode, patients by gender, messages by status, anomalies by category. No money, no ratio, no join beyond one dimension table, no soft-delete surface. Still routed through the DSL, via a generic count(entity) metric.

Target for Phase 1: ~20 metrics, not 60. Grow from the unanswerable log, which is the real backlog.

Response contract

type AnalyticsResponse = {
  id: string;                     // AnalyticsQueryLog.id — feedback + debugging
  status: 'ok' | 'unanswerable' | 'error';

  answer: string;                 // 2–4 sentences. Prose only. Never the source of truth.
  facts: {                        // exactly what the prose is allowed to say
    headline:    { label, value: string, raw: number, unit };
    comparison?: { label, deltaPct: number | null, direction: 'up'|'down'|'flat' };
    highlights:  Array<{ label, value: string, raw: number, sharePct: number }>;
  };

  data: { columns, rows, truncated: boolean, totalRows: number };
  visualization: { type, x?, y[], series?, valueFormat: 'inr'|'int'|'pct'|'minutes' };

  plan: QueryPlan;                // shown in a "How this was calculated" drawer
  provenance: {
    metric:    { id, label, definition };
    timeRange: { from, to, label, timezone: 'Asia/Kolkata' };
    scope:     { branches: string[], role };
    rowCount, executionMs, cached;
  };
  caveats:   string[];            // coverage · flag-null · soft-delete · cell suppression
  followUps: string[];            // 2–3 next questions, generated from the plan

Row budget & cost control

SELECT * is the easy half. The dangerous case is a legal aggregate that explodes.

1 · SELECT * is unreachable, not blocked

The compiler has exactly one output template. There is no branch that emits a bare column list, so no plan shape returns rows. GROUP BY isn't optional — a zero-dimension plan groups by the empty set and returns one row.

SELECT <dimExprs…>, <bucketExpr>, <metric.agg>
FROM   <metric.from + required dimension joins>
WHERE  <baseFilters + timeRange + userFilters + branchScope>
GROUP  BY <dimExprs…>, <bucketExpr>
ORDER  BY <sort>
LIMIT  <n>                        -- appended unconditionally

Equally, patient, bill_number and visit_id are not registered as dimensions at all — unbounded grouping keys don't exist in the vocabulary.

The direct answer

We never feed rows to the LLM. facts.ts sits between the database and the model. Measured on the 9,734-row worst case:

FULL RESULT SET   9,734 rows · 522.8 KB · 133,830 tokens if sent raw
CAPPED (browser)    500 rows ·  26.7 KB
FACTS (to model)      12 highlights · 0.9 KB ·    235 tokens   ← 569× cheaper

The model gets a headline, a comparison, and top-N highlights with their share of total. The full table goes to the user's browser, never to DeepSeek. Token cost is bounded by construction and independent of result size — a 50,000-row aggregate costs the model exactly as much as a 5-row one.

4 · Pre-execution cell estimate — degrade, don't reject

Every dimension carries a measured cardinality in the registry. At validate time, before any SQL runs:

estimate = Π(dimension cardinalities) × timeBuckets(range, grain)
budget   = 1000 cells

Over budget → the compiler degrades and says so. Rejecting a reasonable question is a worse failure than answering a slightly coarser one.

"test orders by test and branch, daily"

as asked       340 × 4 × 71  = 96,560 est.   ✗ over budget
clamp test→20   20 × 4 × 71  =  5,680 est.   ✗ still over
coarsen→week    20 × 4 × 11  =    880 est.   ✓ runs

caveat: "Top 20 tests by volume, weekly. 320 other tests folded into 'Other'."

The ladder is: clamp the highest-cardinality dimension to top-N with an "Other" row → coarsen the grain (day→week→month) → drop to one dimension. Every step appends a caveat naming exactly what happened. The estimate deliberately over-estimates (96,560 predicted vs 9,734 actual — real data is sparse), which is the correct direction for a guard.

5 · Backstops that should never fire

  • LIMIT 500 appended unconditionally — no plan can omit it
  • SET LOCAL statement_timeout = '8s' per transaction
  • Response byte cap — serialize, and above 256 KB truncate with truncated: true
  • analytics_ro cannot write, so a runaway query wastes CPU and nothing else
  • Redis answer cache on plan hash — a repeated expensive question costs nothing twice
Each backstop is an alert, not a silent save

Every firing is logged with its own status. A backstop that fires means the estimator has a gap — that's a bug to fix, not a truncation to swallow.

Conversational analytics

Store plans, not answers. A follow-up is a patch, not a re-derivation.

"Show me diagnostic workload by month."
  → { metric:'test_orders', grain:'month', dimensions:[],
      filters:[{dim:'domain', values:['DIAGNOSTICS']}] }

"Now only Hyderabad."           → patch: { filters: +{dim:'branch', values:['CNT']} }
"Compare that with Balanagar."  → patch: { dimensions:['branch'],
                                           filters:{branch:['CNT','BLN']} }
"Why did it jump in August?"    → decompose(previousPlan, focusBucket:'2026-08')
"As a percentage."              → patch: { metric:'test_orders_share' }

Session state is the last 3 QueryPlans plus their headline facts — roughly 400 tokens, bounded, and immune to prose drift. The model emits {op:'refine', patch:{…}}; the app applies it and re-validates the whole merged plan. Two properties fall out free: the patch is tiny (cheap, low-variance), and a follow-up can never reach a metric or branch that a fresh question couldn't.

The classic bug

The model must also be able to say {op:'new'}. "And what about revenue?" after a workload question is a topic change, not a filter. Getting this wrong silently carries stale filters into a new answer — the signature failure of conversational BI. It gets explicit multi-turn eval cases.

Storage: Redis, 30-minute TTL, keyed userId:conversationId. No new table — conversation history isn't a business record, and persisting analytics questions with their filters is a privacy surface we don't need.

Evaluation & observability

The DSL makes correctness testable: assert on the plan, not on a SQL string.

Plans are normalizable JSON, so equality is exact — unlike SQL strings, where a hundred correct queries are textually different.

npm run eval:analytics — a plain tsx script (no framework; matches smartReport/selfcheck.ts house style). Prints a scorecard and diffs against the previous run, so a model or prompt change is a before/after table, not a vibe.

CI gate

security 100% · money reconciliation 100% · unanswerable ≥ 90% · plan accuracy ≥ 85%. Run against a Neon branch, never prod — branches are data-isolated but not quota-isolated, and heavy testing has suspended the prod DB here before.

What every request logs

One new table, AnalyticsQueryLog, modelled on SmartReport's proven shape.

identity
userId · role · branchScope · conversationId · turnIndex
intent
question · planJson · metric · dimensions · grain · rangeFrom/To · isFollowUp
outcome
status · unansweredKind · retryCount · retryReasons
execution
sqlHash (not the SQL) · rowCount · executionMs · planMs · narrateMs · cacheHit
model
model · promptVersion · inputTokens · outputTokens
output
vizType · answerText (prose only) · feedback 👍/👎
never logged
result rows · bound parameters · raw SQL text · any identifier
retention
180 days, then deleted. Questions are not a business record.

Debugging a wrong answer needs exactly four fields, and they're all there: question → planJson → sqlHash → rowCount. Right plan, wrong number = registry bug. Wrong plan = prompt/catalog bug. That clean split is the point of the DSL.

Alerts: any sql_error (always our bug) · unanswerable >25% (catalog gap) · p95 total >12 s · invalid_plan retry rate >15%.

Roadmap

Two deliberate reorderings from the brief.

Security is Phase 0, not Phase N — the read-only role must exist before the first query runs. The semantic layer is Phase 1, not Phase 3 — in this codebase it is the feature; a metric-free prototype would contradict the Money page on day one, and that lost trust is hard to win back.

PHASE 0~1 day

Foundations — no LLM, no UI

analytics_ro role + grants · lib/analyticsPrisma.ts · AnalyticsQueryLog migration · registry with 3 metrics · plan.ts validator · compile.ts · execute.ts. A tsx script executes hand-written plans; there is no API.

GATE — money reconciles to the paise, and analytics_ro provably cannot write or read a token
PHASE 1~3 days

First answer end to end

Catalog · planning prompt + 8 few-shots · narration + numeric post-validation · facts · logging · registry to ~20 metrics / ~16 dimensions · coverage check. POST /api/analytics/ask. An ask box on /owner: question in, KPI or table out, with the "How this was calculated" drawer. No charts yet.

GATE — 30 example questions answer correctly OR refuse honestly. A confidently wrong number is a failure; an honest refusal is a pass.
PHASE 2~3 days

Dimensions, time series, charts

Deterministic viz.ts · fuzzy name→code resolution · gap-filling · top-N + "Other" · minimum-cell-size suppression · Redis answer cache on plan hash. recharts line/bar/stacked with a table toggle, in ownerUi styling.

Verify in a real browser — tsc does not catch broken hooks or blank pages
PHASE 3~2 days

Comparisons & deltas

compareTo: 'previous_period' through compiler, facts and viz (kpi_delta, paired bars). Quarter and year grains registered but gated on coverage — "last quarter" returns the caveat, not a number.

PHASE 4~2 days

Conversation

Plan patching · Redis session · {op:'new'|'refine'} classification · follow-up chips. Threaded panel; each answer keeps its chart.

The topic-change case that must NOT inherit filters is the acceptance test
PHASE 5~2 days

Evaluation hardening & rollout

Full 120-case suite with run-to-run diffing · 👍/👎 wired to the log · CI gate · small ops view of the unanswerable and retry histograms. Roll out to lab_incharge for operational metrics.

GATE before wider rollout — security 100%, money reconciliation 100%
PHASE 6TBD

Advanced — only what the logs justify

"Why did X change" decomposition (deterministic contribution analysis, model narrates) · anomaly surfacing over AnomalyEvent + z-scores · scheduled digests reusing the WhatsApp sender · the guarded raw-SQL escape hatch — only if the logs prove the DSL is the bottleneck.

PHASE 7optional

Consolidation

Migrate ownerMoneyService / ownerMetricsService onto the registry so there is exactly one definition of every metric. Side effect: replaces ~12 parallel findMany + JS reduction with one GROUP BY — cutting Neon round trips and JS heap on the 512 MB Render box, both open items in the current cost work.

Milestone 0.1 — the exact first commit

Half a day. No LLM. No UI. "The rupee matches, and the role cannot write."

CREATE ROLE analytics_ro LOGIN PASSWORD :'pw';
ALTER ROLE analytics_ro SET default_transaction_read_only = on;
GRANT CONNECT ON DATABASE neondb TO analytics_ro;
GRANT USAGE ON SCHEMA public TO analytics_ro;
GRANT SELECT ON "Visit","Bill","TestOrder","PaymentTransaction","OrderRefund",
                "ReportVersion","DiagnosticReport","TestResult","ClinicVisit",
                "Branch","Department","ClinicalPanel","BillableProduct",
                "TestDefinition","ReferralDoctor","ReferralDoctor_Visit",
                "ClinicDoctor","ExternalLab","MessageLog","AnomalyEvent",
                "DoctorPayoutLedger"
  TO analytics_ro;
GRANT SELECT ("id","gender","yearOfBirth","createdAt") ON "Patient" TO analytics_ro;
GRANT SELECT ("id","name","role","activeBranchId")     ON "User"    TO analytics_ro;
-- everything else, including all three *AccessToken tables, gets NO grant.

Then scripts/analytics-smoke.ts asserts: net_revenue equals ownerMoneyService to the paise · visits by branch by month equals a hand-written control query · analytics_ro gets permission denied on INSERT INTO "Visit", on "ReportAccessToken" and on User.passwordHash · statement_timeout actually aborts pg_sleep(20).

Why this first

If Milestone 0.1's money number doesn't match, we've learned the most important thing about this feature before spending a single token on an LLM.

What we are not building

Each of these is a real fork in the road, declined on evidence.

  • Text-to-SQL as the primary path — Phase 6 escape hatch only, on evidence
  • Vector store / embeddings / RAG over the schema — the vocabulary fits in a prompt
  • LangChain / Vanna / any NL2SQL framework — this is ~800 lines of our own code
  • Materialized views, OLAP cube, star schema, dbt, a separate analytics DB — 311 MB
  • A second LLM provider or a fine-tune — not until the eval set shows a prompt ceiling
  • Multi-agent planning loops — one question, one plan
  • Postgres RLS — every plan is an aggregate; there is no row to filter
  • Streaming responses — a 4-second answer needs a spinner, not SSE plumbing
  • A separate analytics UI framework — ownerUi.tsx + recharts are there
  • Row-level export from the AI surface — the existing pages do it better, with audit
  • Module-enablement infrastructure — keep it isolated so Axora's toggle is mechanical later; don't pre-build the framework
