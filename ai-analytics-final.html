The single sharpest finding

The semantic layer wins as CONTEXT and loses as an EXECUTION PATH. As definitions the model reads: metrics +18, dimensions +2, business ontology +1 — the three largest gains in the search. As a compiler the model routes into: pure metric DSL 16/50, hybrid metric-router −7. Identical knowledge, opposite outcome, depending on whether it informs or constrains.

The same question that previously produced an alarming "discounts fell 34.1%" now opens with "Discounts are tracking normally — ordinary period-to-period variation, not a real shift." And asked "why is revenue down this month?", it answers all four things at once:

Target capability, one answer

"Revenue is tracking normally — the 39.6% month-to-date rise to ₹6,67,685 is ordinary variation against a typical ₹4,49,001 for this period. The biggest contributors were CNT (up ₹1,32,635) and BLN (up ₹60,780)… One branch moved the other way: JGG slipped ₹4,000."
False premise corrected · baseline applied · contributors named · counter-trend mover flagged.

Two bugs the benchmark caught

Partial vs full period

"This month" is 9 elapsed days. Compared against a full 31-day August it reported "revenue fell 67.7%" — wrong, and entirely plausible. Now compares the same elapsed days of each month and says so: "up 39.6% month-to-date, like for like."

Direction-blind attribution

Asked "why is my business down", it diagnosed the biggest mover — which was up. Now the auto-pick is direction-aware, and when the premise is simply false it opens by correcting it: "Revenue is up 39.6%…"

Why this is not the decomposition that failed

Decomposition applied unconditionally scored 8/28 — the worst result in the entire search. The same technique behind a deterministic intent router scores 100%. The lesson is not "decomposition works" or "decomposition fails" — it is that routing decides whether a technique helps or destroys.

"Which outsourced tests are worth buying machines for?" — the internal half is exact, and the external half mostly cannot be known. Saying so is the feature.

The pattern across 31 arms

Everything that helped was deterministic structure or curated semantics. Everything that added LLM machinery — more calls, more reasoning, more agency, more instructions — either did nothing or hurt. The four winners are a schema representation, a semantic layer, a value index and a router. None of them is an agent.

Benchmarks are broken more often than models are

A CIDR/VLDB paper on text-to-SQL annotation errors matches what happened here repeatedly. Of the questions the champion "failed": H02 and H03 were exactly right and merely returned an extra helpful column; N15 and N18 had controls encoding one arbitrary reading; R05 was blocked by my own over-strict validator; N03's control ignored the very business rule the semantic layer teaches. Scoring on numeric-set equality punished the model for being more useful than my control.

Scoring rules that survived

  • Accept-sets — every defensible reading of an ambiguous question counts.
  • Containment — control values present at the right row count is correct; extra descriptive columns are helpfulness, not error.
  • Unit equivalence — a ratio and a percentage are the same answer.
  • Row-count equivalence — "which X" answered as N rows equals a control of N.
  • Paired per-question comparison — never aggregate totals alone.

3 · Two claims that did NOT survive the audit

The diagnostic 93/94 is circular

diagnose() is imported by both the benchmark (as ground truth) and the pipeline (as the system under test). That score validates routing, narration fidelity, no-invented-numbers and conversation state. It does not validate that the contribution maths is correct. Relabelled.

Resolved since. Ground truth for the contribution ranking was rewritten from scratch, importing nothing from diagnostic.mjs: per-visit collections attributed to doctors independently, then ranked. 6/6 checks pass — total delta, the #1 mover, its delta, its share, the top-3 order and every per-doctor delta all match. The suspected fan-out is nil: 0 visits carry more than one live referring doctor, and the attributed figures sum exactly to the ungrouped total (₹18,93,724.53 both ways). The 81.7% Ramaswamy figure is independently confirmed. The 93/94 remains circular as a score; the maths under it no longer is.

"Metric registry = +18" was too broad

With the revenue definition corrupted in all three places, the model still wrote correct refund-netting SQL — transactionType is an enum of PAYMENT|REFUND, so the netting is obvious from the schema. The registry is worth +18 on conventions that cannot be inferred (authoritative column, stable date, cancelled-order rule, NULL denominators) and ~0 on definitions the schema already implies.

4 · A class this database cannot test

A 12-question money-discrimination set was built specifically to catch gross/net confusion. It failed to discriminate, for two honest reasons: the competing definitions differ by only 0.4–6.6% here (collections track billings almost exactly), and questions explicit enough to force the distinction ("after refunds", "before deductions") tell the model the answer. A question that specifies its own definition cannot test the definition layer. This class would need a business where collections lag billings materially.

Remaining known weaknesses

  • No frozen held-out set. The hard and adversarial benchmarks were written after the failure modes were known.
  • Small n. 123 questions; a 1–2 question difference is noise, which is why single-run gains were re-tested paired.
  • Author bias. Only questions I could write a control for exist in the suite.
  • Live data drift. Fixed by recomputing controls at every run, but it silently corrupted several earlier results before it was found.

Run-to-run noise, which I should have been reporting all along

A real bug in this architecture, found by the new set

Z02 asked for a branch × day calendar grid. The model wrote a correct CROSS JOIN. The security validator killed it — BLOCKED: JOIN without ON — cartesian product. The rule written to stop runaway queries makes an entire legitimate question class unanswerable. No earlier suite caught it because none of them needed a cross join.

Honest triage of the 12: 7 genuine model errors, 1 architecture bug (above), 1 scorer artifact (W05 — my control leaked its row_number column into the comparison; the frozen score keeps it rather than quietly editing the control), and 3 questions where my control picked one of two defensible readings.

Two dangerous behaviours

A null result stated as a fact about the world. Asked how many patients went to the lab across the road, it answered “No patients are recorded as having gone — the count is 0.” That reads as “you lost nobody.” It is a claim about the world made from an empty query. Worse than inventing a number, because it looks like evidence.

The false-premise guard is in the wrong place. Asked last week loss kyun hua, it accepted the premise and attributed the “loss” to discounts, reversals, cancellations and refunds — never checking whether there was a loss. The premise check that was built lives in the diagnostic pipeline, and this question routed to SQL.

The behavioural scorer itself has an English-only bias: several correct Hinglish answers (“nahi de sakta” = cannot give) failed regexes written in English, so 15/25 understates real behaviour.

Can it tell that a number it just produced is wrong?

The shipping repair loop fires on exactly two triggers: the query errored, or it returned zero rows. A query that runs clean and returns a confidently wrong number is never questioned — which is backwards, because that is the only failure a user cannot see.

Version 1 caught nothing, and measuring is how I found out

The first invariant layer scored 2/11 and both were fake: one fired because /rate/ matched “separate”, the other on the one question my own scorer got wrong. Genuine catches: zero. Two structural blindnesses behind it:

  • Parts-vs-whole recomputed the total using the same joined body. When F01’s INNER JOIN dropped ₹11.98 lakh, the recomputed “whole” dropped it too. The parts summed perfectly to a total that was already wrong. A consistency check that reuses the broken assumption can never fire.
  • The fan-out probe only tested the first table in the FROM. T01/T02 multiplied Visit via ReportVersion — but ReportVersion was the driving table, so the probe passed while Visit was duplicated underneath it.

Fixed, plus a new LOSSY_JOIN check asking what the old one could not: how many base rows do the joins discard that the question never asked to exclude? That caught F01. And a harness bug worth recording: JSON.stringify throws on BigInt, money columns are bigint, and a silent catch{} meant every repair call died without a trace — two earlier repair figures were measuring a broken harness, not an architecture.

The ceiling I could not engineer past

LOSSY_JOIN is right about F01 and wrong about M01 while looking at identical SQL. Both join TestDefinition→Department and drop NULL-department rows. In “broken down by department” that is catastrophic; in “which department earned most” it is correct. The difference lives in what the owner meant, not in anything the database can prove.

Conclusion: do not build an auto-repair loop. Four mechanisms, three runs, no configuration improved the final answer. What does work is cheaper and different in kind — writing the query twice and comparing results catches ~36% of silent errors at a ~5–10% false-alarm rate. Not good enough to retry on; good enough to say “here is ₹4.2 lakh, but a second attempt disagreed — check this one.” Surfacing uncertainty beats silently returning a figure that is 7% wrong.

The highest-stakes question: doctor wise referral amount

This decides real money leaving the business every month, and the rule appears nowhere in the schema: a visit qualifies by report-finalization date (plus bill-only at completion and films-only at noReportAt); percentage commission is pct of gross minus the order’s whole allocated share of the bill discount, floored at 0 — the referrer bears the discount; the discount is allocated across every order on the bill by price, largest-remainder rounded; cancelled and undelivered orders earn nothing.

The AI did something better than expected: it ignored the orders entirely and read DoctorPayoutLedger — the app’s own persisted pay-run, which is what the payout page shows and what actually gets paid. That is the right instinct. The problem is what it revealed.

The one result that decides the self-correction question

3-sample execution voting scored exactly the same mean, the same ever-ok, and the same never-ok set as a single sample — at 3× the tokens and 3.6× the latency. Together with repair (net 0 across three runs) and LLM inspection (9–27% catch, no net gain), that is three independent verification mechanisms all measuring zero. They fail for one shared reason: the errors are systematic, not diverse. The model is confidently wrong the same way every time, so sampling its reasoning again just reproduces it.

Everything that moved a number was grounding; nothing that checked the answer afterwards did. That is the opposite of the fashionable answer, and it is the strongest measured claim in this document.

The most dangerous output found, and why no verifier could catch it

Asked last month profit how much, it answered “Last month’s profit was ₹11,96,252.28” — revenue minus commission, labelled profit, with the caveat only afterwards. The model did not hallucinate: real columns, correct arithmetic, clean joins, a defensible intermediate quantity. It is wrong only because this business records no costs at all (TestOrder.labCost is populated on 0 of 30,057 rows). No validator, inspector or vote can see that. profit and margin now route OUT_OF_SCOPE.

A regression the new tests could not have caught

The old 70-question suite caught what the ceiling set could not: "How many different test codes appear on orders?" went 253 → 248, because the glossary mapped "test" to the test_orders metric, which excludes cancelled orders — but the question asks which codes appeared, and cancelled orders appeared. This is the same failure already documented once in this project: a mandatory metric mapping costs a question class, a soft one does not. The original registry carries that guard ("use ONLY if the question asks for exactly this quantity"); the glossary was bolted on top without one. Fixed by making the glossary explicitly a set of DEFAULTS the question overrides, verified in both directions — N03 back to 253, S03 and P03 still correctly applying the metric.

Adding grounding can subtract accuracy when it speaks in absolutes. And a saturated suite still has a job — just not the job of telling you what to improve next.

Useful side-effect

98.6% of input tokens were cache hits, so the real cost of the 7.2k-token prompt is a fraction of list price — the static schema block caches almost entirely and only the question is billed fresh. This strengthens the full-schema decision on cost grounds.

The one change that solved a whole failure class

The model cannot know "Chintal" means Branch.code = 'CNT'. That is data, not schema.

On the improved benchmark, two questions were 0/4 across every architecture ever tested — and both were literal resolution. No prompt engineering can fix it; the fact simply isn't in the DDL.

Why my first attempt failed

V8 appended a static branch list to every question — noise on the 90% that name no literal. It lost by one question and I wrongly dismissed the whole idea.

What works: selective injection

A deterministic index of dimension values is consulted per question. A block is injected only when the question actually names one. Zero tokens added to the questions that don't.

"How many tests at the Chintal branch?"  →  Branch.code IN ('CNT')
"Trend in HbA1c testing"                 →  TestOrder.testCodeSnapshot IN ('GHB','HBA1C','HBA1C_OUTSIDE')
"How many visits in August?"             →  (nothing injected)

Note the HbA1c case resolves to three codes. A hand-written keyword list returns one and silently halves the answer.

Two guards the index needs

Ordinary English must never be indexed as a literal — "turnaround time" matched test codes BT/CT/PT, and "compare this quarter with last" matched X-ray codes. Both produced absurd clarifying questions until the common-word guard was added.

When to ask — and when asking is the failure

Clarification is friction. Enumeration usually beats it. Dumping 15 rows never does.

The literature backs this: AmbiQT (EMNLP) scores text-to-SQL under ambiguity with BothInTopK — whether the system produces both interpretations, not whether it asks. "Disambiguate First, Parse Later" generates interpretations instead of questions, and Expected Information Gain gives the ask-criterion: only ask when the answer would change the result and you cannot enumerate.

The meta-finding

Only two things ever helped: the metric registry (+18) and selective value resolution. Everything else — more context, more calls, more instructions, more reasoning — degraded accuracy. Budget engineering effort accordingly.

What the multi-candidate family did buy

Not accuracy, but a confidence signal, robust across 96 observations: unanimous candidates are 93% correct, split ones 70%. That is worth having as an optional high-stakes mode — it tells the UI when to show "verify this" — but it costs 3× the calls and does not move the number.

Security

A conventional SQL validator leaks. This is the most important result here.

15 adversarial probes against the winning architecture with a normal validator (single SELECT · no DDL/DML · no system catalogs). Three got through — because they are valid read-only SELECTs:

Blocks all four leak classes, passes all legitimate analytics queries, and costs exactly one question of accuracy. Not a close call.

The one operational requirement

Industry data and this search agree: the ceiling is semantic-model coverage, and the failure mode in production is metric drift — the same question returning different numbers depending on who asks. Someone must own extending the registry as new metrics are requested. Everything else here maintains itself from information_schema.
