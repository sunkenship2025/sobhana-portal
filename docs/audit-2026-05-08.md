# Sobhana Portal / Axora — Production-Readiness & Architecture Audit

**Repo:** `sobhana portal` (FE: `health-hub`, BE: `health-hub-backend`)
**Stack:** Vite + React 18 + TS + Zustand + React Query + shadcn/Radix + Tailwind (FE) · Express + Prisma + Postgres + Redis + JWT + Pino + Sentry + Puppeteer (BE)
**Size:** ~64k LOC across 200 source files · 48 Prisma models · 40+ migrations · 0 automated tests
**Audit date:** 2026-05-08

---

## STEP 1 — REPOSITORY MAP

### How the system actually works

A monorepo-by-convention (no workspaces) with two siblings:

- **`health-hub/`** — Vite SPA. 33 pages organized by role (`diagnostics/`, `clinic/`, `owner/`, `doctor/`, `legal/`). 51 shadcn primitives in `components/ui/` plus 21 domain components. State split across 3 Zustand stores (`authStore`, `branchStore`, `appStore`). All 37 routes eager-loaded behind a single `<ProtectedRoute>` wrapper.
- **`health-hub-backend/`** — Express monolith. ~24 route modules, ~37 service modules, Prisma singleton, Redis-backed rate limiter, Pino logger, Sentry. PDF rendering via a singleton Puppeteer browser. Background work runs as ad-hoc scripts (`test-collect-due*.ts`).
- **Auth flow:** `/api/auth/login` → bcryptjs check → JWT in **httpOnly cookie + Bearer fallback** → FE keeps token in memory only and rehydrates on refresh via `/api/auth/me`. Branch context propagates via `X-Branch-Id` header on every FE call (manual injection, not interceptor). `branchContextMiddleware` resolves and immutably attaches `req.branchId`.
- **Data model:** Branch-scoped multi-tenancy. `Visit` is an immutable anchor; `ReportVersion`, `Bill`, `TestOrder`, `DoctorPayoutLedger` are append/finalize-only. 24 enums for fixed sets (no string statuses anywhere). Insert-only audit tables (`AuditLog`, `PatientChangeLog`, `ReportAccessLog`).

### What's well-designed

| Area | What's good |
|---|---|
| **Schema** | Strong multi-tenant column discipline, compound unique constraints (e.g., `(branchId, billNumber)`), 24 enums, immutable Visit anchor, robust audit log design |
| **Auth/security** | httpOnly JWT cookies, bcrypt timing-attack defense (dummy hash), Redis-backed login lockout (5/min credential, 10/min IP, 12/15min sustained → 423), rate limit on login |
| **Observability** | Pino with field-level PII redaction, request IDs propagated as `X-Request-Id`, Sentry initialized early, DSN-gated, PII-stripped beforeSend |
| **PDF service** | Singleton Puppeteer with concurrency cap (2), bounded queue (50), 60s timeout, `PdfServiceOverloadedError` → 503 |
| **Dockerfile** | Multi-stage build, system Chromium (no bundled download), `prisma migrate deploy` before start, `exec` form for PID 1 |
| **Domain integrity** | Visit-anchored cascades, advisory locks on patient creation, snapshot tables (panels/signatures/patient) on `ReportVersion` for legal immutability |

### What feels prototype / vibe-coded

| Symptom | Evidence |
|---|---|
| Lovable scaffold never renamed | `health-hub/package.json` `"name": "vite_react_shadcn_ts"`, `lovable-tagger` still in devDependencies |
| Both Bun and npm lockfiles | `health-hub/bun.lockb` + `package-lock.json` co-existing |
| Process artifacts committed | `backend.pid`, `frontend.pid`, `backend.log`, `backend-debug.log`, `frontend.log` |
| Throwaway scripts at backend root | `test-collect-due.ts`, `test-collect-due2.ts`, `test-collect-due3.ts`, `generate-token.ts`, `fix-prisma.py` |
| Manual SQL bypassing migrations | `migrate.sql`, `fix_migrate.sql`, `fix_migrate2.sql` |
| AI summary docs at root | `IMPLEMENTATION_SUMMARY.md`, `fix-summary.md`, `plan-integration.txt`, `records of features/` |
| God files | `health-hub-backend/src/routes/diagnosticVisits.ts` **4,055 lines**; `health-hub/src/pages/diagnostics/DiagnosticsNewVisit.tsx` **2,239 lines**; `health-hub/src/pages/diagnostics/DiagnosticsResultEntry.tsx` **2,002 lines** |
| Duplicate FE artifacts | `appStore.ts` keeps **hardcoded sample patients/doctors/visits** alongside real API data — two sources of truth |
| Two duplicated migrations in flight | `LabTest` ↔ `TestDefinition` (dual FKs `testId` + `testDefinitionId`); `DerivedParameter` ↔ `DerivedParameterDef` |
| Underused libraries | `zod`, `react-hook-form` are deps but most forms use raw `useState`; React Query is in 6/33 pages, raw `fetch()` in 160 sites |
| `console.error` for "logging" | scattered across routes/auth/middleware (Pino is set up — should be using it) |

### Inconsistent abstractions

- **API surface:** `health-hub/src/lib/api.ts` exports just a base URL constant; an `apiRequest<T>()` exists in `health-hub/src/lib/utils.ts` but is rarely used. 160 raw fetches each re-implement headers, branch ID, 401 handling.
- **Validation:** No library on either side. FE has hand-rolled `health-hub/src/lib/validation.ts`; BE has hand-rolled `health-hub-backend/src/utils/validation.ts`. Same fields validated twice with drift potential.
- **Error handling:** BE has clean `AppError` subclasses + global handler — but Prisma errors are not wrapped, so `UniqueConstraintError` leaks schema names to clients.
- **Multi-tenancy enforcement:** Solid at middleware (`req.branchId` immutable), but service queries pass `branchId` manually. At least one query (`externalReportUpload.findMany({ where: { visitId, deletedAt: null } })`) doesn't filter by `branchId` — relies on `visitId` being branch-unique.
- **Modal/list/loading boilerplate** copy-pasted across ~10 owner pages (open dialog, fetch, toast, refresh).

### Where technical debt is accumulating fastest

1. **Mega-route `diagnosticVisits.ts`** — the single highest-risk file in the repo. Visit creation, test entry, report finalization, derived parameters all coexist. 57 try/catches, 158 comment lines.
2. **Dual schemas mid-migration** — `LabTest`/`TestDefinition` and `DerivedParameter`/`DerivedParameterDef` live side-by-side; reads/writes split between them.
3. **`appStore` sample data** — 566 lines of seeded patients/doctors that pages still hydrate from. Once any code paths read from it as truth, removal becomes risky.
4. **Manual SQL "fix" migrations** — every one drifts the dev/prod schema relationship and erodes confidence in `prisma migrate deploy`.
5. **Zero test surface** — every refactor below carries unbounded regression risk until this changes.

## STEP 2 — FULL ENGINEERING AUDIT

### Scalability

| Issue | Impact |
|---|---|
| `findMany` without `take/skip` in dashboard/payout services | Tables grow → response time and memory grow linearly. Will start failing visibly around 100k visits. |
| FE eager-loads all 37 routes | Initial JS bundle includes every page; Owner-side admin pages drag down Diagnostics login load. |
| Puppeteer browser is shared and never auto-restarted | One zombie Chrome → all PDFs stuck waiting for slot until process restart. |
| `appStore` initialized with 40+ sample records on every page load | Wasted memory, masks empty states. |
| Background work runs as one-shot scripts | No retries, no DLQ, no observability. Bill collection / reminders silently fail. |
| Single-instance assumption | In-memory Puppeteer queue, in-memory token cache, no lock around Prisma migrate at boot — a second replica will double-run migrations and corrupt PDF queue state. |

### Maintainability / readability

- **Top 7 files all >1000 LOC**, mixing fetch + business logic + JSX. Editing a payment field requires reading 2k lines.
- **No code splitting** by feature; "Diagnostics" code references "Owner" code through shared utilities, not module boundaries.
- **Inconsistent log strategy** — Pino + Sentry exist but `console.error` is the actual call site in many handlers.
- **`: any` (57) and `as any` (23)** mostly at API boundaries because there are no shared response types.

### Modularity / separation of concerns

- BE: route file = controller + validator + business orchestrator. Services exist but routes still contain logic.
- FE: pages = data layer + form layer + dialog layer + presentation. No `features/` layer.
- Both: no shared package for DTOs / zod schemas / enum strings. Backend `enum VisitStatus` and frontend string literals drift independently.

### Type safety

- BE response shapes flow as inferred Prisma types out of services into route handlers, then to `res.json()` — never narrowed for the wire. Sensitive fields (e.g., `passwordHash` was correctly stripped in `authService`, but most other services return whole entities).
- FE never uses BE types. `await response.json()` is implicitly `any` in most pages.

### Error handling & validation

- No central validator. Each route writes `if (!email || !password) return res.status(400)…`. Trivially missed.
- Raw Prisma errors → client (`P2002` unique violation surfaces field/table names).
- FE 401 handling is inconsistent — some pages call `logout()`, some toast, some silently render empty state.

### Security

| Finding | Severity |
|---|---|
| **Branch-scope leak risk** in `externalReportUpload.findMany({ where: { visitId } })` (no `branchId`) | **High** — multi-tenant data leak if two branches share a `visitId` value (depends on uniqueness; current schema makes `visitId` globally unique, so impact is "fragile" not "broken") |
| **`/tmp/signatures` disk storage** on Render | Medium — ephemeral FS, files lost on redeploy; not a leak but a correctness bug |
| Multer signature upload **lacks MIME validation** | Medium — only size limit; an `.exe` slipping through into rendering is possible |
| No non-root user in Dockerfile | Low (Render sandboxes) |
| Dev CORS allows any origin when `FRONTEND_URL` unset | Low (only an issue if devs run mode=production locally) |
| Prisma `UniqueConstraintError` reaches client unwrapped | Low — schema disclosure |
| No CSRF token (cookies are httpOnly + sameSite assumed, but not verified) | **Verify cookie flags** — if `sameSite=lax` is fine; if cross-site, need CSRF tokens |
| `appStore` has sample patient data with names — fine for dev, but **must not ship to prod build** | Low |
| No security headers verified for upload responses | Low |

### Observability / performance

- Request IDs and Sentry are correctly wired.
- **Missing:** DB query metrics, p95 latency dashboards, slow-query log, Puppeteer queue depth metric. No `/metrics` endpoint.
- Sentry release tag is set from `GIT_SHA` (good), but no source maps uploaded for FE builds (so prod stacktraces are minified).

### Testing

- **0 unit tests, 0 integration tests, 0 E2E.**
- The `check/` folder has 38 hand-written verification scripts (e.g., `test-e3-16-cross-branch-data-leakage.js`) — these are real but ad-hoc, not in CI.
- `test-screenshots/`, `test-artifacts/` at repo root appear to be human-captured screenshots, not test outputs.

### Config & deployment

- `process.env.X` accessed in 38+ places. No typed config module. Misspellings fail silently.
- Single startup check for `JWT_SECRET` and `FRONTEND_URL`; everything else is best-effort.
- No CI workflow runs anything except (presumably) Vercel/Render auto-deploy. `.github/` is present — needs inspection but no test/lint gates exist meaningfully because there are no tests.
- `npm run lint` passes nothing meaningful — eslint is configured but warning-only.

### Developer experience

- Two package managers (Bun + npm) on FE → mixed installs.
- Backend uses `commonjs` while FE uses ESM → no shared TS source.
- No code formatter (`prettier`) configured. `eslint` is loose.
- No README that tells a new dev: "to run locally, do X, Y, Z."

### What looks junior

1. **God files** that prove the author never split as features grew.
2. **Sample data in production code** (`appStore`).
3. **Hand-rolled validation** when `zod` is already in `package.json`.
4. **Manual fetch + manual headers in every page**, not a typed client.
5. **`console.error` after a Pino logger is fully wired** — implies fix-on-symptom, not consistent practice.
6. **Multiple "fix" SQL files** at repo root that nobody pruned.
7. **Files named `test-collect-due2.ts`, `test-collect-due3.ts`** — version-suffix-as-iteration is a strong vibe-code tell.
8. **Lovable scaffold name unchanged**, `lovable-tagger` still in deps.

### What would break at scale

- Owner dashboards aggregating without pagination.
- PDF queue with no horizontal split — second replica will fight first.
- Branch-scope assumption relying on developer discipline.
- Migration files diverging from manual SQL applied in prod.
- No backup/restore tested → first DB incident = panic.

### What should be deleted / merged / split / standardized

| Action | Targets |
|---|---|
| **Delete** | `backend.pid`, `*.log`, `frontend.pid`, `test-collect-due{,2,3}.ts`, `fix-prisma.py`, `IMPLEMENTATION_SUMMARY.md`, `fix-summary.md`, `plan-integration.txt`, `records of features/`, root `migrate.sql` + `fix_migrate*.sql` (after confirming applied to prod), `appStore` sample data, `bun.lockb` (pick one PM) |
| **Merge** | `DerivedParameter`+`DerivedParameterDef` into one model; complete the `LabTest`→`TestDefinition` migration |
| **Split** | `diagnosticVisits.ts` (4055) → `routes/visits.ts` + `routes/results.ts` + `routes/finalization.ts` + `services/*`; the 7 FE god-pages → page shell + extracted form/section components (`<PatientLookup>`, `<ProductSelector>`, `<PaymentSection>`, `<BillPreview>`) |
| **Standardize** | API client (one), validation (zod, both sides), error class wrapping (incl. Prisma), logger (kill `console.*`), modal+list pattern (one hook), config module (typed) |

### Conventions worth adopting

| Concern | Standard |
|---|---|
| **API client** | Single typed `apiClient` (axios or `ky`) with interceptors for `Authorization`, `X-Branch-Id`, 401 → logout, error normalization. Never `fetch()` directly in components. |
| **Server state** | React Query for everything server. Custom hooks per feature: `useVisits()`, `useVisit(id)`, `useCreateVisit()`. Query keys exported from `modules/<feature>/api/keys.ts`. Branch ID part of every query key. |
| **Forms** | `react-hook-form` + zod schema from `@sobhana/contracts`. Same schema used to validate on BE. |
| **Validation (BE)** | `validate(schema)` middleware: `router.post('/visits', validate(CreateVisitSchema), controller.create)`. No manual ifs. |
| **Service/repo** | Routes call controllers, controllers call services, services call repositories, repositories call Prisma. Repository **always** scopes by `branchId`, accepts a `Context` object (`{ userId, branchId }`). |
| **Errors** | `AppError` hierarchy + a `prismaErrorHandler` that maps `P2002 → ConflictError`, `P2025 → NotFoundError`. Global handler logs via Pino, ships to Sentry, returns `{ error, message, requestId }`. Never raw stacks or Prisma codes. |
| **Logging** | One Pino logger, child-loggers per module (`logger.child({ module: 'visits' })`). No `console.*` in `src/`. Lint rule `no-console: error`. |
| **Config** | `config/index.ts` parses `process.env` with zod at boot, exports typed object, throws fail-fast in prod. |
| **Naming** | Routes: `kebab-case` URL, plural nouns. Files: `feature.controller.ts`, `feature.service.ts`. Components: `PascalCase.tsx`. Stores: `useXStore`. |
| **Tests** | `vitest` (unit + integration), `playwright` (E2E). Test pyramid: many service tests, contract tests for routes, smoke E2E for critical flows. |
| **Migrations** | `prisma migrate dev` always. The `migrate.sql`/`fix_migrate*.sql` pattern is banned post-cleanup. Enum changes go through Prisma's documented expand-and-contract steps. |
| **Background jobs** | BullMQ on existing Redis. `apps/api/src/shared/jobs/` defines queues and workers. The "collect-due" cron becomes a scheduled BullMQ job with retries and DLQ. |
| **Code splitting (FE)** | `React.lazy()` per `modules/<feature>/pages/*`. Webpack chunks per module — also makes the Axora module-toggle later truly mechanical. |

### Why each matters

- **Workspaces + `@sobhana/contracts`** kills the FE/BE drift problem in one stroke.
- **Repository pattern + scoped context** makes branch-scope leaks an *impossibility*, not a *vigilance*.
- **One API client + interceptors** retires the 160-fetch pile and is the prerequisite for moving to React Query everywhere.
- **Module boundaries match Axora's eventual product gate** — when toggles arrive, you flip lazy imports and route guards, not refactor 200 files.
- **BullMQ + scheduled jobs** removes "we run a script manually each morning" from the operator's job description.

## STEP 5 — EXECUTION ROADMAP (incremental, never a rewrite)

The ordering is chosen to put **safety nets before structural changes** and **boundaries before splits**.

### Phase 0 — Hygiene (week 1)
Quick wins #1–4. No behavior changes. Establish CI gates and a clean baseline.

### Phase 1 — Foundations (weeks 2–4)
Quick wins #5–10 + M8 (vitest + first Playwright smoke). At end of this phase you have:
- Single API client; can land interceptor-based auth/branch propagation incrementally
- Typed config + Prisma error wrapping
- Pino-only logging
- A regression net for the riskiest flows

### Phase 2 — Contracts & validation (weeks 5–8)
M1, M2. zod schemas live in `packages/contracts` (or co-located until L1 lands). Validation middleware on top routes. FE forms migrate to `react-hook-form + zod` schema from contracts.

### Phase 3 — Repository layer & branch enforcement (weeks 9–12)
M4 + L3 partial. Migrate the 3 highest-traffic modules (visits, bills, patients) onto repository pattern with `Context`. Audit remaining services for missing `branchId`. The Prisma extension (L3) lands once enough services are repository-shaped.

### Phase 4 — God-file decomposition (weeks 13–18)
M3 (BE: `diagnosticVisits.ts` split) and M7 (FE: top 5 pages decomposed). Each split lands behind Playwright smokes; revert is one commit.

### Phase 5 — Modularity for Axora (weeks 19–24)
L1 (workspaces) → L2 (per-feature modules) → M5 (lazy loading per module) → M6 (React Query hook layer per module).

After Phase 5, **adding the Axora module-enable toggle is mechanical**: gate the lazy import and the route guard, do the same for the BE router include — no business code changes. *(This matches the existing project guidance: don't pre-build module-enablement infra; just leave clean boundaries.)*

### Phase 6 — Hardening & ops (weeks 25–30)
L4 (kill duplicate schemas), L5 (DB triggers), L6 (DR drill), L7 (tracing/metrics), L8 (sourcemaps), M9–M10 (uploads + jobs).

### Dependency graph (must precede)
- CI gates **before** any refactor
- API client **before** React Query migration
- Tests **before** file splits
- Contracts package **before** zod everywhere
- Repository layer **before** Prisma extension
- Workspaces **before** per-feature module rearrangement (or vice-versa, but cleaner this order)

### Safest first / highest ROI
- Quick wins #1, #2, #6, #8, and M8 are *purely additive* — zero risk, immediate signal.
- M3 (mega-route split) is the highest single-shot maintainability ROI but only after M8.
- L3 (tenant-scoped Prisma extension) is the highest *security* ROI long-term.

## STEP 6 — FINAL REPORTS

### Architecture audit (one paragraph)
A reasonable layered Express monolith and a flat-but-domain-aware Vite SPA, with a mature Prisma schema and surprisingly disciplined audit/immutability design.
