Clinic doctor login — wireframes

Six screens for a new doctor login in the sobhana portal, designed around the prescription as the reason the login exists. Codebase reality this is built on: UserRole.doctor already exists in the enum but is never used — requireRole is never called with it and the frontend has no doctor routing, so this is a clean slate. ClinicDoctor is a master record with registrationNumber, qualification, specialty — and commissionPercent — and has no link to User. And there is no structured prescription anywhere: today's Rx is a blank sheet printed on letterhead.

Marked open below are the calls I did not make unilaterally — two research passes on clinician access scoping and doctor-portal UX are still running, and those specifics may move.

00

The join that has to exist first

schema

A doctor login is not a new role so much as a binding between an auth identity and a clinical identity. Everything else on this page depends on which way that binding points, so it comes first.

Recommended — ClinicDoctor.userId String? @unique

Nullable, so the 40-odd existing ClinicDoctor rows stay valid and unlogged-in. Unique, so one login is one doctor and the audit trail cannot be shared. The doctor role on User becomes meaningful only when this join resolves — a role:'doctor' user with no ClinicDoctor gets a dead end, not a blank portal.
  • Direction matters: putting clinicDoctorId on User instead would let two users point at one doctor. Rx signatures must be attributable to one human.
  • Gate before shipping: confirm zero prod User rows already have role='doctor'. The enum value is vestigial in code, which is not proof it is unused in data.
  • ClinicDoctor is not branch-scoped — a doctor can hold visits at several branches while User.activeBranchId is singular. The queue must scope by active branch and say which branch.
  • Add hprId String? — optional, and leave it optional. ABDM's Healthcare Professionals Registry is voluntary; practice licensing runs through NMC / State Medical Councils, which HPR explicitly does not replace. HPR holds ~10.5 lakh professionals across all categories against 1.3–1.5M registered allopathic doctors alone, so requiring an HPID would lock out most clinic doctors today. Store it for the ABDM path later; never gate login on it. (NMC's draft National Medical Register regulation of Aug 2026 may change this — worth re-checking before the ABDM work starts.)
The commission problem

ClinicDoctor carries commissionType, commissionPercent, commissionAmountInPaise and consultationFeeInPaise on the same row as the doctor's name and qualification.

The moment a doctor can read their own ClinicDoctor record, they can read their own commission terms — and GET /clinic-doctors/:id returns the whole row today.
  • Fix at the serialiser, not the query: a doctorSafeClinicDoctor() projection that drops the four money fields, used by every doctor-scoped route.
  • Same class of leak in GET /visits/clinic/:id, which returns consultationFeeInPaise — the very endpoint the existing prescription print page calls.

The design rule this forces. The research on chart review says a doctor scans problems, active medications, recent results first. We have exactly one of those three. So the doctor's patient view cannot be a thin imitation of a full EMR chart — it has to be a superb diagnostics view plus a prescription history, and be honest that that is what it is. What this means for sequencing Vitals and a problem list are each a small table and a form. Worth deciding deliberately rather than discovering during extraction.
00c

Diagnostics are OFF by default

reversal of my earlier ruling

I had ruled diagnostics in — "withholding a lab result from a treating doctor is the bigger risk." Overruled, and the default flips: a clinic doctor sees no test values and no list of tests done. It is one org-wide setting, shipped false, and the code path simply does not fetch.

Mechanism — reuse AppSetting, the org-wide key/value table that already holds report_auto_sync_default. One row:
key   doctor_view_diagnostics
value "false"  ← ships like this
  • Enforce on the server, not by hiding a panel. When false, the doctor-scoped Patient 360 endpoint must not return test orders or results — a hidden div is still a payload, and the payload is what leaks. Same discipline as the money projection in §00.
  • What disappears with it: the abnormal-result badge on queue rows, the lab lines in the consultation left pane, the Reports and Abnormal-results glance cells, the results inspector, and the Results nav item — which is why that nav item is gone entirely rather than conditionally rendered.
  • What survives: everything about prescriptions and consultations. That is the doctor's own record of their own work, and it is never gated.
  • The honest cost. This is a real clinical trade-off, not a free one: a doctor prescribing for a patient whose potassium came back at 6.8 will not see it here. Worth naming plainly, and worth revisiting per-clinic rather than pretending the default is costless.
What the inspector looks like if a clinic turns it ON. Built to the research, kept here rather than thrown away — three severity tiers, tabular figures, and a distinct “range not reported” state.

01b

Who moves the queue — every flow

staff and doctor, never one or the other

The rule that makes all of this tractable: the queue state and the prescription state are two separate machines. WAITING → IN_PROGRESS → COMPLETED is where the patient is. DRAFT → … → SIGNED is what the prescription is. Signing may nudge the queue as a convenience, but neither state ever requires the other — the moment they are coupled, a doctor cannot close a visit without prescribing, and a patient cannot be moved along while a draft sits open.

  • “Call next” is not a new idea in this building. The waiting-room display already calls tokens. The doctor pressing Call next should be what makes the TV announce the number — one action, the patient hears it, the row goes in-progress, the composer opens. That is the single highest-value button on the whole screen.
  • Search never starts a visit. Opening a chart to read is not the same act as beginning a consultation, and conflating them would silently mark patients in-progress from across the building.
The four awkward cases, decided 1 · “Done, no prescription” must exist. Not every consultation produces one. Without this button doctors will create an empty prescription purely to close the visit, and the record fills with noise that looks like clinical data.

2 · Staff marking Done while a draft is open is allowed. Front desk must be able to keep the queue moving; blocking them on a doctor's unfinished work would jam the clinic. The draft is not destroyed — it drops into the amber strip and ages there. Staff sees a quiet note, not a blocker: “Dr Ramesh has an unsigned prescription for this patient.”

3 · Signing after COMPLETED is allowed. The patient has left, the doctor finishes writing. Refusing this would mean either a lost prescription or a fake reopen. The prescription records its own signing time; the queue does not care.

4 · The signer is stored, never derived. ClinicVisit.clinicDoctorId is assigned; who actually signed goes on the prescription row. If a colleague covers, reassignment and authorship stay independently true.
Accidental finalisation — the one to design against. Sign & next is fast by design, which is exactly what makes a mis-tap expensive. Two cheap guards: the review screen in §03 is a separate screen with its own attestation, and the signed prescription stays amendable by revision for the rest of the session, which is a new version with a reason rather than an edit. No undo, no silent mutation.

  • “not stated” is a value. Amlodipine has no timing because the doctor did not say one. The box shows not stated in italic grey — never a helpfully invented "before breakfast". Unknown stays unknown.
  • The “Not captured” box is the most important thing on this screen, and the least obvious. Across published audits 54–86% of ambient-scribe errors are omissions — and omissions are the class nobody catches: automated reviewers score near coin-flip on them (AUC 0.50–0.63) for the blunt reason that an omission leaves no text to point at. Aviation research puts humans at missing up to 55% of omission errors versus ~0% for active wrong statements. A passive grey "not stated" inside a card is not enough; what is expected and absent has to be stated out loud, in its own box, or it is invisible.
  • Tier the friction — do not spread it evenly. The strongest causal result in all the research: severity-tiered drug-interaction alerts lifted compliance from 10% under flat alerting to 29% overall, and to 100% versus 34% on the most severe tier. So a hard, active confirmation belongs on drug identity, strength, dose and route only. Timing, duration and instructions get a light touch. One uniform "approve all" is exactly the rubber-stamp shape that decays with use.
  • Sign is disabled while anything is unconfirmed — and disabled in the API too, not just here. The button being grey is a courtesy; the state machine is the control.
  • Source line per medicine, with timestamps, collapsed by default behind source. The doctor checks the machine by reading what they actually said.
  • “Repeat 2 Sep Rx” may matter more than the microphone. Represcribe-from-last is the one speed feature present in every product surveyed — US and Indian alike — and it targets the same bottleneck dictation does, with none of the transcription risk. Build it alongside voice, not after.
  • Picker rules, from the strongest safety finding in the research. 18 of 23 prescribers in one qualitative study named juxtaposition errors — picking the entry next to the one intended in an autocomplete list — as something they had actually done. So: full generic name + strength + form on every candidate, never truncated; never auto-select the top match on Enter or Tab; and look-alike names deliberately separated rather than left alphabetically adjacent. The two Augmentin options above are stacked and spelt out for exactly this reason.
  • Keyboard: / new medicine, ⌥M mic, Tab across fields, ⌘↵ review. A doctor who never touches the mouse must be able to finish — but Tab moves between fields and never commits a drug choice.

The failure mode this screen exists to catch — and the one reviewers miss most A 2026 adversarial audit of three deployed commercial scribes over 565 notes found 31.3% carried at least one verified failure. The class adversarial reviewers caught least often — 4.5% — was plans written as done. Their own example is almost exactly our problem: a choice between two drugs recorded as two issued prescriptions.

Say “either azithromycin or amoxiclav, let's start with the azithro” and a fluent extractor emits two medicines. Both look perfect. Neither is flagged. The paper's line is the one to design against: “The failures easiest to miss are the fluent ones. A reviewer scanning for what looks odd will not catch them.”

Which is why the sheet shows what was spoken next to what was extracted, and why the count of medicines deserves to be read out loud in the attestation — “2 medicines” — rather than left to be inferred from a list the eye slides down.
Signature — resolved, and the existing stack is the right answer Telemedicine Practice Guidelines §3.6.4.2 requires the RMP to provide a “photo, scan, digital copy of a signed prescription or e-Prescription.” A signature image is the one method the guideline expressly names — so the existing base64 per-(branch, department) signature stack is already the defensible mechanism, not a stopgap. No Digital Signature Certificate is demanded by any health-sector rule found.

What to avoid is the opposite end: a typed name alone satisfies neither IT Act §3 nor §3A, so it gets none of §5's deeming-equivalent-to-handwritten protection. It is the only option with zero primary-source backing. If you want the strongest footing later, layer Aadhaar eSign (§3A-compliant) on top of the image.
Two hard requirements, not preferences 1 · Registration number. §3.2.5, verbatim: “Every RMP shall display the registration number accorded to him/her by the State Medical Council/National Medical Commission, on prescriptions, website, electronic communication (WhatsApp/ email etc.) and receipts etc.” So Reg. 54821 is mandatory on the sheet above — and on the WhatsApp message that carries it, which is a template change, not a UI change.

2 · Schedule X and NDPS are a hard block. §3.7.4 prohibits prescribing Schedule X drugs or any NDPS-listed narcotic or psychotropic over telemedicine, absolutely, with no exception in any source found. This belongs in the deterministic validator as an un-overridable gate on any non-in-person path — not a warning the doctor can dismiss.

05b

A prescription is a third artefact, exactly like a bill and a report

old and new workflow both keep working

Patient 360 already knows how to own a document: a bill and a report each have a token, a public link, an access log, a cached PDF, a WhatsApp send and an inspector section. A digital prescription is the third one and should be built from the same parts — no new concepts. And almost all of those parts turn out to be generic already.

• a signed digital prescription exists → render it, with view / print / send, like a report
• none exists → the blank-sheet button, unchanged
• both remain available — a doctor who wants a blank sheet to hand-write on still gets one, even on a visit that has a digital Rx

Nothing is migrated and nothing is retired. Every visit before this ships has no prescription record and correctly shows the blank-sheet button forever. A doctor with no login, or one who prefers paper, loses nothing. Voice is an accelerator on top of a typed editor, which is itself an accelerator on top of a printed blank sheet — and all three layers stay standing.
Where it differs from a report, and must. A report is authored by the lab and released to the patient. A prescription is authored by the doctor and is the doctor's own signed instrument. So: the signer is the consulting doctor, not a department rule (§07b); it may never be auto-sent (§29 of your brief); and amendment creates a revision with a reason rather than a new report version cloned by staff.
Carry the registration number onto the WhatsApp template. §3.2.5 requires it on prescriptions and electronic communication. The REPORT and BILL templates never needed it; the PRESCRIPTION one does, and it is the kind of requirement that gets missed precisely because it lives outside the UI.

Why the evidence is one-sided. Every documented clinical-privacy incident found was standing access misused, never a break-in — UCLA staff browsing celebrity charts (US$865k settlement), 23 security guards at one hospital opening 419 records with no job need (US$240k), ~50 employees fired at another for one patient's ER record. All were caught by reading logs afterwards. Regulators' own remedy, imposed after the fact, was to narrow access to what each role needs — which is the design decision in front of you now.

still open Whether an Indian clinic will tolerate that friction at OPD volume is the owner's call. But the default should start locked and be loosened deliberately, never the reverse.
DPDP does not hand you a continuity-of-care exemption. Unlike HIPAA's treatment carve-out, the DPDP Act's §7 "legitimate uses" cover only a medical emergency (threat to life or health) and epidemic/public-health response. There is no general treatment or continuity-of-care legitimate use. So routine internal doctor access rests entirely on the "specified purpose" in your §5 patient notice — which means how broadly that notice is worded is load-bearing, and is a drafting decision, not an engineering one.

Timing buys room: DPDP's substantive duties commence around 13 May 2027 (Consent Manager registration ~Nov 2026). Until then the 2011 SPDI Rules remain operative — and those do classify medical records as sensitive personal data, where DPDP's own text notably does not.
Enforcement note. Every "no" above has to be a route guard. Three of the leaks are already live in endpoints the doctor portal would legitimately need to call — GET /visits/clinic/:id returns consultationFeeInPaise, GET /clinic-doctors/:id returns commission, and the Patient 360 summary returns outstandingDueInPaise. A doctor-scoped projection layer is not polish, it is the first task.

Session behaviour — the finding that surprised me most. An anonymous survey of 299 healthcare workers found 73.6% had used a colleague's password — and 100% of medical residents had, averaging nearly five episodes each. Credential sharing is not an edge case; it is what clinicians do when re-authentication is slow, and it destroys every audit and break-the-glass control on this page at once.

An unsaved prescription must survive a lock — a lock that discards work teaches doctors to share a login.
07b

Signatures — reuse the signing stack, but not the rule engine

one new column, no new concepts

The portal already has a complete signature stack: SignatureEditor with the background removal, signatureImage.ts, base64 storage that survives a Render deploy, and the reveal animation. All of it is reusable as-is. What must not be reused is SigningRule — and that distinction is the whole design.

Why a prescription gets no signing rule. A SigningRule answers “which doctor signs this department's reports” — it exists because a pathology report has no inherent author, so config has to name one. A prescription already knows its author. It is ClinicVisit.clinicDoctorId — the doctor who saw the patient.

Adding a rule layer would let configuration contradict reality: a rule could name Dr A while Dr B actually consulted and signed. For a legal instrument carrying a registration number, that is the one failure mode worth designing out entirely.

What I would build first

The login is worth shipping before voice, and each step leaves something usable.

  • 1 · The join and the deny list. ClinicDoctor.userId, requireRole('doctor') on everything, and the money projection. No new screens. Nothing works yet, nothing leaks.
  • 2 · Today + clinical Patient 360. A doctor can log in and read. Genuinely useful on its own, and it surfaces the access-scoping decision against real users rather than in the abstract.
  • 3 · Typed prescription, signed. The structured Rx model, the state machine, the immutable signed version, print onto the letterhead the portal already renders. This is the feature — it replaces a blank printed sheet with a record. Voice is an accelerator on top of it.
  • 4 · Drafts. Falls out of the state machine, and is needed before dictation makes drafts common.
  • 5 · Then voice, into fields that already exist and are already editable and signable.
Why this order If voice comes first, the prescription model gets designed around what the extractor happens to emit. Building the typed editor first forces the schema to be right for a doctor typing at 11 a.m. with no microphone — and that is also the fallback every failure mode in the VoiceRx brief needs.
09

What this is actually based on — and how good the evidence is

Separating the measured from the merely conventional, because the two should not carry equal weight when you disagree with one of them.

Measured — large-sample or controlled

  • EHRs score 46/100 on the System Usability Scale (n≈870, replicated at n=848). 68 is "acceptable"; 46 is a failing grade and the bottom decile of all benchmarked software. The bar to clear here is low.
  • Wrong-item-from-dropdown is a lived error, not hypothetical — 18 of 23 prescribers reported making juxtaposition errors. This is the single finding that most changed the wireframes (§02).
  • Computerised prescribing cuts prescribing errors ~48% vs paper — the case for replacing the blank printed Rx sheet at all, independent of any voice feature.
  • Clinicians prefer structured/tabular displays over narrative summaries, rating them lower effort. Drove the tabular results panel in §05.
  • Personalisation is one of four measured satisfaction drivers across 35,000+ physicians (KLAS). Favourites and persisted defaults are not polish.
  • Raw responsiveness outranks features in physician complaints — 47% call response time inadequate.
  • ~16 minutes of software time per outpatient encounter, of which documentation and ordering are ~41%. That is the budget this feature is competing for.

Convention — strong, universal, but not a study

  • "Don't show doctors the money." No study tested whether showing a bill amount changes prescribing. What is evidenced is the underlying mechanism — visible referral economics altering ordering behaviour is why Stark-type law exists. Every product surveyed keeps billing out of the clinical chart. I am confident in the rule; I am not going to call it proven.
  • Three-list dashboard layout. Universal across independently built competitors, which is real but weak evidence. No vendor publishes usability data on it.
  • Break-the-glass. Accepted practice, explicitly not a universal regulatory mandate.
The India-specific divergence worth taking seriously. Indian OPD products — HealthPlix, Eka Care, DocOn, and the existing voice-Rx products already in this market — all market prescription speed as the core differentiator, several claiming under a minute. HealthPlix's own finding from 6,000 clinics was that Indian doctors wanted one simplified view, not more information. So the density model to copy is theirs, not Epic's. That is also the honest competitive context for VoiceRx: structured voice-to-Rx in Indian languages is an existing product category here, not an unclaimed idea.
Primary-source legal requirements — build these, don't debate them
  • Registration number on every prescription and every electronic message carrying one — TPG §3.2.5.
  • Schedule X / NDPS: hard block on any non-in-person path — TPG §3.7.4, no exception exists.
  • A signature image is expressly endorsed; a typed name alone has no statutory footing.
  • Individual logins are non-negotiable if any of the audit design is to mean anything.
  • Access logs: DPDP Rule 6 wants visibility through logs, monitoring and review, retained one year.
  • Breach notice has no materiality threshold — every affected patient, plus the Board, detail within 72 h.
  • Erasure (§8(7)) yields to statutory medical retention — so keeping full history stays correct.
Needs a lawyer, not me — four that actually block things 1. How broadly the patient notice defines "specified purpose", since that — not statute — is what makes a second doctor's access lawful. 2. Whether the NMC 2023 conduct regulations are still in abeyance, i.e. whether the 2002 regime and the 2020 Telemedicine Guidelines are in fact today's operative rules. 3. Signature sufficiency for Schedule H/H1 dispensing — no Indian judgment or CDSCO/PCI circular was found either way, an explicit negative finding. 4. If psychiatry is ever in scope, the Mental Healthcare Act 2017 runs its own confidentiality regime that can override the patterns on this page, and needs its own review.

Anti-patterns to avoid on purpose

  • Dismissible warnings. The most important number in this research: published clinical-decision-support alert override rates run 49–96%. A warning a doctor can wave away becomes trained-out noise within weeks — so it is not a safety control, it is a liability that looks like one. Design consequence for the validator: a rule either blocks finalisation or it is not worth showing. The Schedule X block is the former. There should be very few of them.
  • Dark theme as the default. Counterintuitively wrong for this room: dark backgrounds behave more like a mirror under strong ambient light. A light theme with strong contrast is the better default in a sunlit Indian clinic.
  • Clearing a field when validation fails. Forces re-entry of data that was already correct. NHS calls this out explicitly. Show errors only on submit — never while typing or on blur — with a summary at the top linking to each invalid field.
  • One visual treatment for doctor and patient. Direct evidence says these must differ in density and in colour use: clinicians want tiers and trend, patients want plain language and calmer colour. Relevant to us specifically — Smart Reports must not inherit this page's palette.
  • Binary red/green flagging and sub-24px targets, per §05 and the table opposite.
A real conflict between two research passes, resolved Security says a shared clinic workstation should idle out in 2–5 minutes. NHS accessibility says if a multi-step form has an inactivity limit it should be ≥ 20 hours, so nobody loses work mid-shift.

Both are right about different objects. Lock the screen fast; never discard the draft. The session expires in minutes, the prescription in progress survives until the doctor resolves it — which is also what §04 and §07 already needed independently.
India accessibility — not binding on us yet, but moving. The RPwD Act 2016 routes ICT duties at GIGW 3.0 (WCAG 2.1 AA, 88 mandatory checkpoints), which binds government and PSU sites, not a private clinic SaaS. But IS 17802 is harmonised with EN 301 549 and is trending mandatory for regulated private sectors — SEBI has already imposed it across financial services — and a Nov 2024 Supreme Court ruling held accessibility standards must become mandatory rather than advisory. Meeting WCAG 2.2 AA now is cheaper than retrofitting it when healthcare's turn comes.
