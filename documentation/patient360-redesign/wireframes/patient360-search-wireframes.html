Patient360 — Search / Entry Page

Replacing the two-button "Search by Phone / Search by Name" toggle with one smart search bar that accepts phone, name, patient ID, or bill number and routes accordingly. Greyscale, placeholder data, for review before code.

The core idea
  • One input, no mode toggle. Type anything; the system detects the type and shows a small "Detected: …" label you can override.
  • Phone → all matching patients (handles family members sharing a number). Name → matching patients. Patient ID (e.g. P-01432) → that patient. Bill no. (e.g. MPR-2231) → resolves to the patient + jumps to that visit.
  • No match → a clear "Register new patient" path (walk-in), instead of a dead end.
  • backend-dep Today the API searches phone / name / email only. Patient-ID and Bill-no. lookups need a small backend add.

1 · Default (empty) — one bar + accepted inputs + recent patients

No black/grey toggle buttons. The placeholder itself teaches what's accepted. "Recently viewed" gives the front desk a 1-tap path back to the patient they just had.

Detection rules & what needs backend
  • Detection (frontend, instant): contains @ → email · matches ^P-?\d+ → patient ID · looks like a bill number (branch-prefix + digits, e.g. MPR-2231, or a leading #) → bill · all digits & length ≥ 7 → phone · otherwise → name. A wrong guess is one tap to override.
  • Already works: phone, name, email search (GET /patients/search).
  • backend-dep Patient-ID search — add patientNumber to the search service.
  • backend-dep Bill-number lookup — resolve a bill number → its visit + patient, to power Frame 3 (jump-to-visit).
  • Debounced live results (type-ahead) vs. press-Enter is an open choice — see question to owner.
  • Shared-phone disambiguation (Frame 2) is the key safety behavior and needs no backend change.
