Pulse artifact audit

Read against the implementations: artifacts.ts, capability.ts, contract.ts, tools.ts, run.ts, PulseArtifacts.tsx. Every claim below traces to code, not to filenames.

Executive diagnosis

The richness is mostly already in Evidence and reaches the browser. The renderers throw it away. run.ts:409 puts the full evidence[] on the wire alongside the artifact specs — summary, data.rows, metric, unit, dimension, means, period. Artifact({a, evidence}) resolves the step and hands the renderer the whole object. Nothing is lost in transit.

So the blame does not mostly sit with the data model. It splits three ways, and they need different fixes:

Renderers display a fraction of what they receivePulseArtifacts.tsxlargest

The two specific bugs in your screenshot

1. "CT ORDERS BY TEST TYPE (90 DAYS)" is not a breakdown. It is a histogram. That render is the Distribution component: it finds one numeric column, cuts it into 10 equal buckets, and draws the frequency of counts. The footer — median 2 · 90th 22 · worst 22 — is the spread of the order-count column, not the test types. The title and the rendering describe different things, there are no category labels because a histogram has no categories, and nothing in the pipeline noticed.

How it was selected: describeEvidence set numericSpread: true (≥6 rows, >15% range). distribution requires exactly that, so it became admissible. The job was opportunity, which no renderer declares in expresses, so every candidate got the same +0.08 consolation and distribution won on prefers:['numericSpread'] +0.15. A truthfulness gate passed; an analytical-usefulness gate does not exist.

2. The two artifacts came from a generated query step, which is the poorest evidence Pulse produces. A registry breakdown returns {total, parts:[{name, value, change, shareOfChangePct}], period, metric, unit, dimension}. A query step returns {question, rowCount, rows}. No total, no unit, no period, no dimension, no share. The renderer cannot show a denominator that was never computed.

Architecture diagnosis

LayerVerdict
Database / SQLFine. Registry tools return rich, correct aggregates.
Evidence structureFine for registry tools. Thin for generated queries — no total, unit, period or dimension is ever attached.
Artifact schema on the wireNot the problem. {type,label,evidence} is thin, but the full Evidence travels beside it and the renderer gets both.
Capability selectionTruthfulness gate works. No analytical-usefulness gate — and the score spread (0.23–0.38) is too flat to separate a good representation from a merely legal one.
LLM artifact generationFine. It picks a type and a step; it should not be inventing metadata.
Frontend renderersThe main problem. Each renders 20–40% of what it is handed, and seriesOf() discards every column beyond the first label and first value.

Proposed model

Not a new schema — a derivation step between evidence and render, because the facts are present and nobody computes the second-order ones.

Always, when knownOnly when it earns its place
Headermetric · unit · period (explicit dates) · scope · row count vs showncomparison period, incompleteness
Rowslabel · valueshare of total, delta, rank gap, tag (new, walk-in)
Footertotalconcentration (top-N share), remainder, share of change, n, definition

Same earns(evidence) predicate discipline as requires/buildable: a share column appears when a total exists; a delta appears when prev exists; a concentration line appears when rows > 5. A field that cannot justify itself is absent, not faint.

Migration — three levels

LevelChangeBuysCost
1 — renderer only Stop discarding. Header line from metric/unit/period/dimension. Share-of-total from total. Delta from prev. Remainder row. Fix seriesOf to keep all columns. ~70% of the damage. No backend change, no model change.~1 day
2 — evidence enrichment t_query attaches what it can infer deterministically: column totals, row count, the resolved period and scope from the spec (which it now receives as a binding). Fixes the screenshot path specifically~half a day
3 — capability Add a continuous structure flag so distribution cannot claim categorical evidence. Add an analytical-usefulness term so a renderer that expresses no job loses to one that does. Kills the category error~half a day

Level 1 first, alone, and measure. It is the cheapest and the largest, and it needs nothing from the model or the database. Level 3's usefulness gate should be designed only after seeing which renderers are still mis-selected once they actually display their evidence.

What not to do

  • Do not add fields to the artifact schema. The information is already on the wire. Adding total, share, period to the spec would make the LLM responsible for metadata it should never author.
  • Do not make the model write metadata. Every number it authors is a number that can be wrong and must then be grounded. Totals and shares are arithmetic — derive them.
  • Do not give every artifact the same header. A KPI with a period, scope, comparison and definition line is four lines of chrome around one number.
  • Do not make the frontend infer analytical meaning from raw rows. seriesOf() already guesses which column is the label and which is the value; that guessing is why columns get dropped. Derivation belongs in a shared, testable layer.
  • Do not rewrite the artifact system. The capability contract — hard requires, real buildable, no question text — is sound and was expensive to get right.
  • Do not tune scoring constants first. The flat 0.23–0.38 spread is a symptom of a missing dimension in the model, not of badly chosen numbers.
